# Kubernetes Service Discovery

Prefer the runtime skill `kubernetes-service-discovery-runtime` when it is available. That runtime skill is generated by the companion extension and contains a per-execution snapshot of service-related Kubernetes APIs discovered from the current cluster.

## Flow

1. Load `kubernetes-service-discovery-runtime` near the start of cluster-facing work.
2. Reuse the discovered `kind`, `groupVersion`, and `resource` values instead of guessing CRD names.
3. Confirm concrete objects with bounded reads such as `exec_kubectl` and `-o json` before writing.

## Rules

- Treat the runtime snapshot as the source of truth for the current worker execution; it is relevance-filtered by default to exclude irrelevant service-name false positives.
- If a service-related API is absent from the snapshot, do not assume it exists.
- The snapshot is fetched once per execution; do not expect it to reflect later CRD installs or removals during the same run.
- Even though the snapshot is relevance-filtered, perform explicit bounded reads (e.g., `exec_kubectl -o json`) to confirm object-level existence and details before writing.
- When discovery fails, fall back to explicit bounded reads instead of inventing APIs.
